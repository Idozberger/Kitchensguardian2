# Ручне тестування — гілка `feat/perfomance-optimization`

Гілка попереду `main` на 8 комітів + є незакомічені зміни. Незакомічені зміни — це і є основна
робота з продуктивності (lazy loading списків); коміти додають ще кілька фіч, що потрапили в цю
гілку. Нижче — все, що варто прогнати руками, по пріоритету.

---

## 🔴 High priority

### 1. Unit system (Metric / Imperial) — вибір системи вимірювань
**Де:** діалог створення кухні (Home → Create Kitchen) → дропдаун "Measurement System";
Profile page → селектор одиниць виміру.

**Кроки:**
1. Створити нову кухню, обрати **Imperial** → перевірити, що в Pantry / Add Item
   дропдауни одиниць показують oz/lb/tsp/tbsp/fl oz/cup/quart/gallon (не grams/kg/ml/litre).
2. Як **host**: Profile → змінити Metric ↔ Imperial → має зʼявитись тост "Measurement system
   updated.", а Pantry/Grocery/Recipes мають одразу показати нові підписи одиниць (без
   перезапуску застосунку).
3. Як **не-host (member)**: спробувати змінити систему на Profile → має бути тост
   "Only the host can change the measurement system.", значення не змінюється.
4. Item зі старим/легасі рядком одиниці (наприклад "piece", "count") — має відображатись як
   "Unit", без дублів чи крашу.
5. Відкрити дропдаун вибору системи **всередині діалогу створення кухні** — перевірити, що
   опції не обрізаються (там `ClipRRect`, це відомий ризик).
6. Закрити й відкрити застосунок з активною кухнею на Imperial — одиниці мають бути
   правильними одразу, ще до відповіді з мережі (беруться з локального кешу).

**Що вважати регресією:** опції дропдауна обрізані/невидимі в діалозі створення кухні;
не-host зміг змінити систему; одиниці "залипають" старими після перемикання доки не
перезапустиш застосунок; краш на невідомому рядку одиниці.

### 2. Онбординг — новий порядок кроків + новий слайд "Scan Your Products"
**Де:** реєстрація → підтвердження email → вибір/створення кухні → карусель фіч (тепер 4
слайди) → скан холодильника/кухні (тільки для host) → dashboard.

**Кроки (пройти всі шляхи):**
1. Новий юзер реєструється, підтверджує email → має потрапити на **Kitchen Selection**
   (НЕ одразу в онбординг-карусель, кухня більше не створюється автоматично).
2. Створити нову кухню → далі має показатись карусель з 4 слайдами; перевірити 4-й слайд
   "Scan Your Products" (оранжевий градієнтний фон, "матова" картка, картинка продукту всередині
   SVG-рамки сканування, білий текст заголовка).
3. Завершити карусель як **host** без storage areas → має вести на скан
   холодильника/кухні.
4. Завершити карусель (або натиснути Skip) як юзер, що **приєднався** до існуючої кухні
   (member) → має йти одразу на dashboard, НЕ на скан кухні, навіть якщо та кухня ще не
   відскановна.
5. Вийти і зайти знову після завершення онбордингу → карусель НЕ має зʼявлятись повторно
   (прапорець `onboarding_completed` зберігається на бекенді).
6. Натиснути **Skip** на будь-якому кроці карусели → миттєвий вихід, без зависання/спінера.

**Що вважати регресією:** онбординг показується двічі; member потрапляє на екран сканування
для host (там інша логіка прав); кухня створюється автоматично без вибору юзера; Skip не
реагує.

### 3. Скан чека (Receipt) — lazy-список + lazy-декодування thumbnail + robustness
**Де:** Pantry → Scan Receipt → сторінка деталей відсканованого чека; Pantry → Scan Meal (камера).

**Кроки:**
1. Відсканувати чек з великою кількістю позицій (10+, бажано 50+) → список має скролитись
   плавно, без фризу при першому відкритті (thumbnails не мають декодуватись усі одразу, лише
   по мірі скролу); картинка чека — завжди перший елемент зверху.
2. Швидко натискати +/− на кількості позиції, довести до 0 і спробувати ще раз зменшити →
   кількість має зафіксуватись на 0, без крашу і без відʼємних значень.
3. Вручну відредагувати кількість позиції на порожнє значення, "0", "-5", нечислове →
   має зʼявитись помилка валідації "$назва: quantity must be a valid number greater than 0.",
   збереження не проходить.
4. Якщо можливо змоделювати відсутність файлу фото чека на диску (наприклад, система
   почистила кеш) і спробувати сканувати → тост "Receipt photo could not be found. Please
   retake the photo.", без крашу.
5. Зробити фото в Scan Meal → перевірити, що воно стискається (менший розмір), але якість
   візуально прийнятна; фото коректно відображається і завантажується.
6. Зберегти відсканований чек у Pantry, перевірити, що thumbnails позицій після збереження
   відображаються коректно (без биті картинки/чорних квадратів).

**Що вважати регресією:** фриз/лаг при відкритті великого чека; краш на граничних значеннях
кількості; краш при відсутньому файлі фото; одна "погана" позиція ламає весь скан (має
пропускатись, а не валити всю партію); зображення biті/порожні після round-trip збереження.

**Edge case:** чек з 0 позицій → список показує лише картинку чека, без крашу.

### 4. AI-іконка / фото товару — заміна base64 на URL + fallback-ланцюжок
**Де:** My Pantry, Grocery (усюди де рендериться іконка товару).

**Кроки:**
1. Відкрити My Pantry з товарами, що мають AI-іконку, але без фото користувача → іконка має
   підвантажуватись з мережі (`icon_url`), а не з base64.
2. Товар без фото і без `icon_url` → показується стандартна сіра іконка-заглушка
   (`Icons.food_bank`), без "битої картинки".
3. Товар з фото користувача → фото має пріоритет над AI-іконкою.
4. Старі товари (додані до цього фіксу) vs нові відскановані — обидва мають коректно
   відображати іконки.

**Що вважати регресією:** biта іконка (broken image), нескінченний спінер, показ заглушки
там, де мало бути фото/іконка.

### 5. Прапорець "needs_review" (низька впевненість AI-розпізнавання)
**Де:** Receipt review (деталі скану чека), Kitchen Analysis page (Smart Kitchen Setup).

**Кроки:** відсканувати чек/фото кухні, у якому бекенд позначить хоча б одну позицію як
`needs_review`. *(Це керується AI-впевненістю бекенду, можливо буде потрібен тестовий
акаунт/дані з відомим результатом.)*

**Очікується:** позначена позиція має оранжеву рамку картки + оранжеву іконку-трикутник
попередження зверху праворуч; при першому завантаженні списку, якщо є хоч одна така позиція —
одноразовий тост "Some items had low detection confidence — please review them before
confirming."; якщо позначених немає — тосту немає.

**Що вважати регресією:** немає візуальної відмінності позначених позицій; тост зʼявляється
повторно або не зʼявляється взагалі; краш, якщо в JSON відсутнє поле `needs_review` (має
безпечно трактуватись як `false`).

## 🟡 Medium priority

### 6. Лайк-рецепти (Favourite Food) — lazy-список
**Де:** Planner → Favourite Food page.

Відкрити з 30-50+ обраними рецептами, поскролити вниз і вгору. Заголовок "Your all favorite
food list" має лишатись зверху, скрол — плавний без затримки при відкритті. Порожній список
обраного — має показувати окремий empty-state (не список).

### 7. Generate Recipes — секції "Generated" і "Saved Recipes"
**Де:** Planner → Generate Recipes page.

Згенерувати кілька рецептів (або мати кілька збережених), поскролити всю сторінку. Обидві
картки мають зберегти вигляд білої картки з рамкою і заокругленими кутами; елементи всередині
не мають накладатись один на одного або мати пропущені відступи. Порожній стан "No Saved
Recipes here!..." має відображатись коректно.

### 8. My Kitchen Members — список учасників
**Де:** Dashboard → Kitchen → My Kitchen Members.

Відкрити кухню з 5+ учасниками, поскролити. Заголовок "All Kitchen members" лишається зверху,
роздільники між учасниками на місці (не зайві/не відсутні), блок сповіщень під списком
працює і не "розʼїжджається" по висоті. Edge case: кухня з 0-1 учасником — без крашу.

### 9. Автопідказки назви товару в "Add Item"
**Де:** Pantry → Add Item (ручне додавання) → поле "Item name".

Ввести частину назви ("mil", "che", "app") — через ~300мс має зʼявитись список підказок.
**Важливо:** каталог захардкоджений (~40 позицій: Milk, Eggs, Butter, Cheddar Cheese, Yogurt,
Bread, Bananas, Apples, Oranges, Tomatoes, Potatoes, Onions, Garlic, Carrots, Broccoli,
Spinach, Chicken Breast, Ground Beef, Salmon Fillet, Shrimp, Bacon, Rice, Pasta, Olive Oil,
Flour, Sugar, Salt, Black Pepper, Coffee, Tea, Orange Juice, Almond Milk, Peanut Butter,
Honey, Ketchup, Mayonnaise, Mustard, Cereal, Oats) — для решти запитів відсутність підказок
це нормально, не баг. Ввід довільного тексту все одно має проходити (це не обмежений вибір).

### 10. Grocery list — lazy-список + фікс скролу
**Де:** Grocery page.

Список 20+ позицій, скрол вгору/вниз, чекбокси. Стан "відмічено" не повинен "перескакувати"
на інший товар під час скролу/ребілду.

### 11. Scan History — пагінація
**Де:** Scan/Receipt History page.

Список з 2+ сторінками історії, доскролити до кінця. Має підвантажувати наступну сторінку
без дублів і зупинятись на реальному кінці списку (раніше був баг: параметр `page` взагалі не
надсилався на бекенд).

### 12. Smart Kitchen Setup — помилка сканування + повтор
**Де:** Smart Kitchen Setup → Kitchen Analysis page.

Змоделювати помилку скану (вимкнути мережу під час завантаження фото) → має зʼявитись
червона іконка + "Scan failed" + повідомлення + кнопка "Try Again". Під час завантаження
кнопка підтвердження має показувати спінер і бути недоступною для повторного натискання.

## Примітка
Секція A (коміти `15fb683`…`201045e`) і секція B (незакомічені lazy-loading зміни) описані
разом, бо всі вони фактично зараз в одній гілці. Юніт-тести, що документують точну очікувану
поведінку lazy-списків, лежать у `test/*_lazy_test.dart` — варто прогнати їх (`flutter test`)
перед ручним QA, вони ловлять регресії типу "повернувся `SingleChildScrollView`" автоматично.
